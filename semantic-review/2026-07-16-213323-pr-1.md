## High-level view

Safe Edit batches, explicit checkpoint/entry restores, and renderer-triggered manual captures acquire `fileMutationQueue` before `snapshotQueue`. Snapshot-only operations never acquire the workspace coordinator, and the additional Safe Edit FIFO sits outside both, leaving no reverse lock edge or deadlock cycle.

Incomplete guarded rollback persists a recovery hold before queued retention resumes. Reloaded holds survive restart, deferred Clear, TTL/count pruning, and object GC; a complete whole-checkpoint restore releases the hold only after every entry succeeds, while partial or single-entry restore leaves it intact.

Clear explicitly abandons idle recovery holds but only defers deletion for an active lease. If that lease subsequently needs recovery, hold promotion cancels the older deferral. Lease-cleanup errors remain non-fatal to the established file result and retain current-process protection when recovery persistence or loading fails.

### Acyclic ordering across Safe Edit and snapshot actions

The only direct `captureFiles()` callers are Safe Edit, already inside the shared coordinator, and the manual-capture IPC handler, which enters that coordinator first (`apps/desktop/src/main/services/safeEdit.ts:224-272`, `apps/desktop/src/main/ipc.ts:1387-1396`). Explicit entry and checkpoint restores use the same order internally (`apps/desktop/src/main/services/snapshots.ts:301-362`).

```text
Safe Edit FIFO -> fileMutationQueue -> snapshotQueue
manual capture -> fileMutationQueue -> snapshotQueue
entry/checkpoint restore -> fileMutationQueue -> snapshotQueue
clear/list/read/prune/GC ----------------> snapshotQueue
```

The coordinator remains held across each multi-file commit or restore, so app-owned operations cannot produce the prior mixed successful state and manual capture observes a complete before- or after-state.

### Recovery-hold transitions preserve data until resolution or abandonment

A Clear encountered during an active lease keeps the run and marks deferred deletion. Incomplete rollback then removes that marker, records the run in `recovery-holds.json`, and only afterward applies retention, all inside `snapshotQueue` (`apps/desktop/src/main/services/snapshots.ts:403-472`). On restart, hold loading precedes every path that can prune or abandon protected data; `persistPruned()` force-adds protected entries after ordinary retention planning before calculating the GC reference set (`apps/desktop/src/main/services/snapshots.ts:51-79,165-182`).

Whole-checkpoint restore removes a hold only for a non-empty checkpoint with no failed entry; partial and single-entry restores preserve it (`apps/desktop/src/main/services/snapshots.ts:301-362`). A later Clear removes idle holds as an explicit abandonment. Safe Edit catches lease-release/retention failures after determining the file outcome and adds a warning without changing `ok`, `applied`, or `recoveryRequired`; failed hold persistence leaves the in-memory recovery set intact, while failed hold loading leaves the active lease intact (`apps/desktop/src/main/services/safeEdit.ts:242-264`, `apps/desktop/src/main/services/snapshots.ts:403-429`).
