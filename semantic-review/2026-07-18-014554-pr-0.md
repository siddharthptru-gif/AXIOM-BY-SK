# Persisted workspace trust and Restricted Mode (final review)

Three actionable gaps remain. **High, confirmed:** a surfaced persistence error aborts `workspaceTrustSet(false)` before Main cleanup, even when rename already committed the revoked state. **High, confirmed:** active agents are outside Main's workspace-revocation lifecycle and can continue tools after trust is removed. **Medium, confirmed:** MCP status and manual disconnect discard each connection's root, allowing one workspace view to display or tear down another workspace's servers. The change otherwise uses canonical Main-owned persistence and fail-closed renderer state.

**Watch for:** **HIGH — confirmed:** failed revocation persistence skips all process teardown; **HIGH — confirmed:** active agents remain Main-authorized after revocation, including `run_command`; **MEDIUM — confirmed:** MCP listing and id-only disconnect are global rather than workspace-scoped.

**Verdict**: NEEDS_CHANGES

## High-level view

The trust store correctly surfaces non-`ENOENT` I/O failures, but revocation cleanup runs only after `setWorkspaceTrust` resolves. **High, confirmed:** a failure before return—most importantly parent-directory sync after a successful rename—can leave workspace processes alive while the persisted state is already restricted.

The renderer requests agent cancellation when its workspace capability disappears, while Main gates only `agentRun`. **High, confirmed:** active controllers have no workspace association, tools do not recheck trust, and an in-flight shell command does not observe cancellation.

MCP calls compare against the canonical root retained on each connection. **Medium, confirmed:** the status and disconnect APIs lose that root, so `McpView` treats the global connection list as owned by its current workspace.

## Revocation cleanup is skipped when persistence reports an error

**Severity: High. Confidence: confirmed.** The atomic writer renames the new trust file and then syncs its parent directory (`apps/desktop/src/main/services/workspaceTrust.ts:134-135`). A supported parent-sync failure is rethrown (`workspaceTrust.ts:110-118,136-139`), so `setWorkspaceTrust` rejects instead of returning its state (`workspaceTrust.ts:162-174`). The IPC handler awaits that result before entering any cleanup (`apps/desktop/src/main/ipc.ts:624-640`).

If rename succeeds and parent sync reports an I/O error, disk now says the root is untrusted, but terminals, LSP, MCP, extensions, and debug remain alive because the handler never reaches their teardown. An earlier write failure has the same cleanup omission; although the old trust decision remains persisted in that case, an authorized explicit revoke request still fails open for already-running resources. This conflicts with the required surfaced I/O errors and fail-closed revocation behavior.

Canonicalize and authorize the root before persistence, then run trust-independent workspace cleanup for every `trusted === false` request even when persistence throws, preserving the original I/O error for the caller. Cleanup should attempt every subsystem independently so one teardown failure cannot suppress the rest.

## Agent execution is outside Main's revocation boundary

**Severity: High. Confidence: confirmed.** Main checks trust before `runAgent` (`apps/desktop/src/main/ipc.ts:1197-1223`), but revocation stops terminals, LSP, MCP, extensions, and debug only (`main/ipc.ts:629-640`). Active agent controllers are keyed only by run id, `cancelAgent` has no workspace association (`apps/desktop/src/main/services/agent.ts:1319-1326`), and default tools do not recheck persisted trust.

`AgentPanel` requests cancellation on capability loss (`apps/desktop/src/renderer/src/workbench/AgentPanel.tsx:109-123`), leaving enforcement dependent on renderer cooperation. The `run_command` tool awaits `runShellCommand` (`apps/desktop/src/main/services/agent.ts:744-746`), which spawns without the run's abort signal (`agent.ts:539-541`), so a command can continue until exit or the 60-second timeout after cancellation.

Associate active runs with their canonical root, add a trust-independent `cancelAgentsForWorkspace(root)` to revocation, and propagate cancellation into spawned commands. Recheck trust immediately before approval-gated tools while keeping `agentCancel` available in Restricted Mode.

## MCP teardown is global despite root-bound connections

**Severity: Medium. Confidence: confirmed.** Each MCP connection stores `root` (`apps/desktop/src/main/services/mcp.ts:49-55`), but `listConnections` omits it and returns every connection (`main/services/mcp.ts:284-290`). Main exposes that global list and an id-only disconnect (`apps/desktop/src/main/ipc.ts:1646-1649`).

`McpView` stores an unfiltered response as the current workspace's state and later disconnects every locally stored id on capability loss or unmount (`apps/desktop/src/renderer/src/workbench/McpView.tsx:40-68,72-95`). A stale response after a root switch is dropped while the view remains mounted, so a connection not yet in `connectionsRef` can also survive the transition and be adopted by the next root's global refresh. With multiple roots or windows, one view can therefore display another root's tools and terminate its connections.

Scope connection listing and disconnect by canonical root or by sender plus root. Disconnect should remain trust-independent, but Main should authorize the root and verify connection ownership before terminating it.
