# Trust-boundary blocker re-review (v2)

This focused pass finds no HIGH blocker, but three MEDIUM blockers remain in the requested paths. Blockers (1), (2), (3), (7), and (8) are closed; (4), (5), and the power-loss durability portion of (6) are not fully closed. The remaining failures are confined to renderer-delivery confirmation, managed-settings identity across symlinks, and write-ahead journal ordering.

**Watch for:** **MEDIUM, confirmed** approval activation treats an asynchronous IPC send as renderer delivery; **MEDIUM, confirmed** a symlinked managed `settings.json` bypasses runtime-policy adoption; **MEDIUM, likely** the profile rollback journal is not ordered durably against the two preference replacements.

## High-level view

**MEDIUM, confirmed:** Main activates an opaque preview token after `webContents.send()` returns rather than after the renderer acknowledges receipt. A renderer crash, navigation, or listener loss in that interval can leave an approval pending indefinitely and hold an agent slot despite the cancellation and supersession invalidation.

**MEDIUM, confirmed:** the managed-file marker is recorded under the lexical settings path, while filesystem save canonicalizes the full path before checking that marker. A symlinked settings file falls through to an ordinary write and leaves Main policy stale.

**MEDIUM, likely:** profile journal contents are synced, but directory-entry ordering is never synced. The rollback record is therefore not guaranteed to reach durable storage before either preference replacement after power loss.

## Approval activation stops at IPC enqueue, not renderer receipt

**MEDIUM, confirmed.** The agent activates the exact-preview token as soon as `wrappedEmit()` returns true (`apps/desktop/src/main/services/agent.ts:1224-1240`). The Main bridge returns true immediately after `sender.send(IPC.agentEvent, e)` (`apps/desktop/src/main/ipc.ts:1032-1035`), but `webContents.send()` is asynchronous and provides no receipt acknowledgement. Preload only subscribes to the event (`apps/desktop/src/preload/index.ts:387-390`); there is no delivery-ack channel. If the send is accepted and the renderer then crashes, navigates, or loses the listener before handling the preview, the token is marked active while no renderer owns it, and the approval promise has no timeout.

Add an acknowledgement carrying the run ID and exact preview token after renderer receipt, transition the pending request from prepared to active only for the matching generation, and reject it on acknowledgement timeout. Cancellation and supersession must invalidate both prepared and active states so a delayed acknowledgement cannot reactivate an obsolete preview.

## Canonicalization drops the managed Settings identity

**MEDIUM, confirmed.** `ensureSettingsFile()` records the lexical path in `resolvedSettingsFiles` (`apps/desktop/src/main/services/settings.ts:124-135`), then IPC separately authorizes that path (`apps/desktop/src/main/ipc.ts:604-612`). On save, `filesystem.writeFile()` first resolves the full path through `assertAuthorizedPath()` and only then asks `writeResolvedSettingsFile()` whether it is managed (`apps/desktop/src/main/services/filesystem.ts:76-80`). For a final symlink, or a symlink/junction in the user-data ancestry, the canonical path no longer matches the registered lexical key; `writeResolvedSettingsFile()` returns `null` at `settings.ts:143-144`, so the generic write runs without the `applyRuntimeSettings()` call at `settings.ts:148-150`. Editing `ai.safety.*` or update settings through that managed tab therefore updates disk while Main retains the prior policy.

Carry the managed scope through authorization as a Main-owned capability, or register and revalidate the canonical save identity rather than comparing unrelated pre- and post-canonicalization strings. Add final-symlink and symlinked-ancestor saves to the equivalence regression: disk normalization and Main egress/update policy must match an equivalent Settings UI commit.

## The profile rollback record lacks durable namespace ordering

**MEDIUM, likely.** `atomicWrite()` syncs the temporary file contents and then renames it (`apps/desktop/src/main/services/profilePreferences.ts:47-58`), but it never syncs the parent directory. The transaction then renames the journal, settings, and keybindings and removes the journal in sequence without a directory flush between phases (`profilePreferences.ts:180-184`). Filesystem namespace operations are not durably ordered by file-content sync alone, so power loss can persist a preference replacement without the rollback journal, or persist journal removal before both committed replacements are durable. Recovery has the same ordering gap when it restores both files and removes the journal (`profilePreferences.ts:102-115`).

Use write-ahead ordering: durably install the journal and flush its parent before touching either preference, durably install both preference replacements and flush the parent before removing the journal, then durably flush the removal. Apply the same restore-both/flush/remove/flush sequence during recovery, with a platform-appropriate write-through primitive where directory handles cannot be synced.
