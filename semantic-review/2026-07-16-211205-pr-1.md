# Endpoint-bound BYOK and serialized Safe Edit recovery (v4)

The four v3 findings are addressed at their original boundaries: Main binds stored BYOK credentials to normalized endpoints, modify/delete edits require SHA-256 source hashes, rollback targets only committed paths, and snapshot index/object transactions are serialized under leases. Those constraints now survive renderer, preload, Main IPC, and provider-service handoffs. Two recovery-lifecycle races remain, and the security/data-loss changes have no persistent automated regression coverage.

**Watch for:** **MEDIUM — confirmed:** snapshot restores and Safe Edit commits use independent queues and can report success with a non-serializable mixed file state; **MEDIUM — confirmed:** incomplete rollback releases its lease, so a deferred Clear can delete the only recovery data; **MEDIUM — confirmed:** no automated tests exercise endpoint binding, mandatory hashes, snapshot leases, or guarded recovery.

**Verdict**: NEEDS_CHANGES

## High-level view

Main now owns the credential-to-endpoint association. Renderer and preload calls carry provider identity, requested base URL, ordinary headers, and write-only key input; Main resolves a normalized endpoint/key/revision tuple before every chat, agent, review, compose, completion, inline, commit-message, probe, and fallback path reaches `guardedFetch`.

Safe Edit now models create, modify, and delete as distinct contracts. All three production producers hash their source content, IPC independently requires a SHA-256 digest for modify/delete, and Main revalidates after capture and before commit before constructing guarded rollback requests from committed paths only.

The snapshot service serializes capture, list/read, restore, clear, prune, GC, and lease release. Clear defers active-run deletion, but the snapshot queue is independent of Safe Edit’s apply queue and lease release does not distinguish complete from incomplete recovery.

No repository test harness exercises these contracts; only build and typecheck scripts are present.

<summary>Issues (3)</summary>

1. **Independent file-mutation queues — MEDIUM, confirmed** — Snapshot restore and Safe Edit can interleave across the same files and both report success with a mixed result. Put Safe Edit commit/rollback and snapshot restore under one Main-owned file-mutation coordinator.
2. **Incomplete recovery releases its lease — MEDIUM, confirmed** — Safe Edit unconditionally releases the checkpoint after a partial rollback, allowing a deferred Clear to delete the returned `runId` and its objects. Retain recovery-needed checkpoints until recovery succeeds or is explicitly abandoned.
3. **Trust and recovery fixes lack regression tests — MEDIUM, confirmed** — No automated tests cover endpoint authorization, hash coercion, queue ordering, deferred clear, or guarded rollback. Add deterministic service and IPC tests with controllable I/O barriers.

### Main-issued endpoint/key pairs gate every AI egress path

Preload requires an `AiCredentialBinding`, and `secretsSet` validates the provider/base URL pair before `setAiCredential()` writes it (`apps/desktop/src/preload/index.ts:245-251`, `apps/desktop/src/main/ipc.ts:613-619`). `normalizeAiBaseUrl()` canonicalizes scheme and host, removes trailing path slashes, preserves case-sensitive path/query data, rejects URL credentials/fragments, and applies the egress protocol policy (`apps/desktop/src/main/services/secrets.ts:179-218`). Store reads, writes, deletes, binding checks, and legacy revision migration pass through one promise queue (`apps/desktop/src/main/services/secrets.ts:52-66,231-274,284-348`).

An unbound built-in key is restricted to its registry default, an unbound Custom key cannot be used until re-entered, and an existing Custom key cannot silently become keyless at another endpoint (`apps/desktop/src/main/services/secrets.ts:284-337`). A freshly supplied Custom probe key may go to the explicitly entered normalized endpoint because that key is already renderer-known; a blank probe key must resolve the stored Custom binding (`apps/desktop/src/main/ipc.ts:405-424`).

```text
Renderer action
      |
      v
Preload IPC -> Main coercion -> resolveAiCredential(provider, baseUrl)
                                      |
                         endpoint + key + revision
                                      |
 chat/fallback | agent | review/compose | completion/inline/commit | probes
                                      |
                                      v
                    provider-family dispatch -> guardedFetch
```

Primary chat and each fallback resolve independently (`apps/desktop/src/main/ipc.ts:646-724`); Agent resolves before `runAgent` (`apps/desktop/src/main/ipc.ts:895-930`); Review and Composer resolve before their services (`apps/desktop/src/main/ipc.ts:1045-1095`); completion, inline edit/chat, and commit-message handlers resolve settings-derived endpoints (`apps/desktop/src/main/ipc.ts:1122-1295`). Test Connection and Fetch Models use the Custom probe resolver (`apps/desktop/src/main/ipc.ts:634-640`). Provider dispatch owns the final credential-header rejection, and every provider network call uses `guardedFetch`; the only other direct Main `fetch` is the unrelated updater (`apps/desktop/src/main/services/ai.ts:408-604`, `apps/desktop/src/main/services/aiGateway.ts:257-319`).

### Mandatory source hashes survive renderer, preload, and Main coercion

The shared edit type cannot represent hashless modify/delete operations, and runtime validation rejects malformed hashes (`apps/desktop/src/common/safeEdit.ts:13-36,75-113`). Chat hashes the text read before its code-block replacement, checkpoint review hashes the `data.cur` source used to construct selected hunks, and Composer retains each reviewed old-text hash for modification and deletion (`apps/desktop/src/renderer/src/workbench/ChatPanel.tsx:260-282`, `CheckpointsView.tsx:265-289`, `ComposerPanel.tsx:151-167,259-288`). Main reconstructs each variant from untrusted IPC values and rejects absent/non-hex hashes before stage or apply (`apps/desktop/src/preload/index.ts:548-553`, `apps/desktop/src/main/ipc.ts:1406-1458`).

Main validates before capture, revalidates after capture, and checks each target immediately before rename/delete (`apps/desktop/src/main/services/safeEdit.ts:181-203,227-242`). Recovery derives requests from `applied`, associates each with Axiom’s committed content, and checks that expected state directly before restore; untouched targets are excluded (`apps/desktop/src/main/services/safeEdit.ts:91-168`, `apps/desktop/src/main/services/snapshots.ts:217-255,318-350`).

### Independent restore/apply queues permit a mixed successful outcome

**MEDIUM — confirmed.** Safe Edit releases the snapshot queue when leased capture returns, then commits under its own `applyQueue` (`apps/desktop/src/main/services/safeEdit.ts:233-241,263-265`). User restores run under `snapshotQueue` and write files without participating in `applyQueue` (`apps/desktop/src/main/services/snapshots.ts:263-290`); the renderer exposes restore without a cross-service activity lock (`apps/desktop/src/renderer/src/workbench/CheckpointsView.tsx:76-101`).

For files A and B, Safe Edit can commit A, a checkpoint restore can restore A and B, and Safe Edit can then commit B. Both operations report both paths successful, but the final state is restored A plus edited B, which matches neither serial order. Use one Main-owned file-mutation coordinator for Safe Edit commit/rollback and snapshot entry/checkpoint restore, with lock ordering that cannot deadlock the snapshot metadata queue.

### Incomplete rollback can return a dead recovery run ID

**MEDIUM — confirmed.** Guarded recovery returns unresolved committed paths and the checkpoint `runId` when a target changed after Axiom wrote it (`apps/desktop/src/main/services/safeEdit.ts:136-160`), but `applyEditsLocked()` calls `releaseCheckpointLease()` for every result (`apps/desktop/src/main/services/safeEdit.ts:239-258`).

Clear retains an active run only until release and records it in `clearAfterLease` (`apps/desktop/src/main/services/snapshots.ts:365-379`). Release removes the run from `leasedRunIds`; `persistPruned()` then filters the deferred-clear run out and garbage-collects its objects (`apps/desktop/src/main/services/snapshots.ts:127-145,355-360`). The renderer can receive unresolved `applied` paths and a `runId` whose snapshot has already gone. Preserve incomplete-recovery checkpoints as durable recovery state and honor deferred clear only after recovery completes or is explicitly abandoned.

### Critical trust and recovery schedules have no regression tests

**MEDIUM — confirmed.** Neither package defines a test command, and no test/spec or assertion-based test files cover the reviewed services (`package.json:10-16`, `apps/desktop/package.json:8-15`). Not tested: endpoint mismatch and legacy-key migration under concurrent secret operations; every AI handler’s resolver use; hashless IPC rejection; capture versus clear/prune/GC; clear during incomplete rollback; and interleaved restore/Safe Edit schedules. Add deterministic service tests with temporary stores and controllable I/O barriers, plus IPC contract tests for all edit variants and AI egress callers.

`git diff --check` found only LF-to-CRLF warnings. Node and web TypeScript checks were attempted, but the command runner did not return a trustworthy completion status or diagnostics, so they are not counted as passing.
