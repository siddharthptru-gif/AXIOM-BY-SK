# Local-first workbench settings, profiles, and overlays

Task #2 connects settings, keybindings, profiles, account/onboarding, update/About surfaces, notifications, and Project Intelligence without gating the local workbench on authentication. Three correctness gaps remain. Profiles ignore their settings payload, startup mutations can replace persisted whole-object stores from an unhydrated snapshot, and Output silently loses older notification history. **Watch for:** **HIGH, confirmed** — profile `settings` payloads have no effect; **MEDIUM, confirmed** — pre-hydration settings or keybinding writes can erase persisted entries; **MEDIUM, confirmed** — Output discards entries after 500 notifications.

## High-level view

**HIGH, confirmed:** The portable profile envelope accepts settings, but the profile UI neither captures nor applies them. Include the intended settings in the profile and apply them with the preset/editor/active-profile fields in one `setMany` update.

**MEDIUM, confirmed:** Revision refs protect React state and Main queues write order, but neither makes a whole-object payload based on the initial empty state fresh. Gate mutations until hydration or move patch/revision merging into Main.

**MEDIUM, confirmed:** Output entries are independent from the four live toasts, but a separate 500-entry slice still deletes history. Remove that eviction or retain the complete history outside the rendered list.

## Portable profiles ignore their settings payload

**HIGH, confirmed:** `SettingsProfile` includes a `settings` record, and the common profile helpers preserve it. `saveCurrent` in `ProfilesView.tsx:69-75` constructs profiles without settings, while `apply` at `ProfilesView.tsx:84-94` sends only `keymap.preset`, `editor.keymap`, and `keymap.activeProfile` through `setMany`. A valid imported profile can therefore report success while every stored setting remains unchanged. Capture the intended settings when saving, then merge `profile.settings` with authoritative profile metadata in one `setMany` call.

## Pre-hydration writes can erase persisted preferences

**MEDIUM, confirmed:** The settings store begins its read at `settings/store.tsx:106-118`. If a command calls `set` first, `persistUser` at `settings/store.tsx:209-215` writes a whole object derived from the empty ref. The read callback later merges disk data into memory after noticing the revision change, but never writes that merged object back, so the file remains stripped to the early mutation.

The same race loses keybindings outright: a mutation writes the sparse object at `commands/keybindings.tsx:187-195`, then the revision check at `commands/keybindings.tsx:122-127` discards the startup snapshot. Main’s serialization queues guarantee operation order and atomic file replacement, not payload freshness. Prevent mutations until hydration and replay queued patches, use Main-owned patch/CAS operations, or persist the merged hydration result before marking the store loaded.

## Output evicts retained history

**MEDIUM, confirmed:** `notifications/store.tsx:20-21` defines limits of 500 Output entries and four live toasts, and the subscriber slices `entries` at `notifications/store.tsx:53-60`. The 501st event silently deletes the oldest Output row despite the explicit Clear action and the retained-history requirement. Keep the toast cap, but remove Output eviction or move complete history to a retained backing store while virtualizing the visible list.
